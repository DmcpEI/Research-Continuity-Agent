# Evaluation

RCA is evaluated at two layers:
- retrieval quality: does the correct paper surface in the top-k bundle?
- generation quality: does the final answer cite the correct source, use retrieved evidence, and abstain when the corpus does not support the question?

This document reflects the current **129-question** evaluation corpus and the current eval scripts in the repo.

---

## Golden Set

The active golden set is [eval/golden.json](../eval/golden.json).

- Total questions: `129`
- Answerable: `90`
- Negative / unanswerable: `39`
- Difficulties: `15 easy`, `62 medium`, `52 hard`

Coverage includes:
- single-paper factual lookup
- method and contribution questions
- paraphrase / lexical mismatch cases
- cross-paper comparison
- multi-chunk synthesis
- explicit negative / unsupported queries

Negative questions `neg-011`–`neg-039` carry a `negative_type` field so abstention can be reported per failure mode:

| `negative_type` | Count | Meaning |
|---|---|---|
| `unreported` | `10` | paper is in the corpus, the asked detail is not |
| `false_premise` | `7` | question assumes a method, setting, or result the paper does not have |
| `out_of_corpus` | `4` | real system or benchmark that is not in the corpus |
| `fabricated` | `4` | invented paper or system name |
| `off_domain` | `4` | topic unrelated to the corpus |

Each new negative was checked by pattern search over all chunk text; candidates the corpus answers even partially were dropped (for example AutoBag's 500 g YuMi payload). The original `neg-001`–`neg-010` are untyped.

Metric definitions:
- `citation_precision`: fraction of answerable, non-abstained cases where every expected source appears in the returned citation IDs
- `abstention_recall`: fraction of negative questions where the system abstains correctly
- `grounded_rate`: fraction of all cases where the model returned a cited answer; for reporting, the more meaningful view is answerable questions answered with citation
- `keyword_hit_rate`: fraction of `expected_keywords` matched by case-insensitive substring in the generated answer
- `hit@k`: retrieval-only metric indicating whether the expected source appears in the top-k resolved retrieval hits

## Generation Harness

```bash
uv run python eval/harness.py --model qwen3.5:4b
```

`--split test` (or `dev`) runs only that split's questions from `eval/splits/`. The published
scorecard is made from one such test-split run with the shipped defaults:

```bash
uv run python eval/harness.py --split test
uv run python eval/scorecard.py eval/results/run_<timestamp>.json
```

`scorecard.py` refuses runs from a dirty tree, a degraded index, with errors, with a component
that fell back (reranker, query rewrite, facts check), with questions other than the committed
test split, or with non-default settings; otherwise it writes `eval/scorecard.json` and the
scorecard block in README.md and here.

Optional model override for direct A/B runs:

```bash
uv run python eval/harness.py --model llama3.1:8b
```

The harness runs [GenerateFlow.generate_answer()](../rca/flows/generate_flow.py) over all `129` questions and records:
- `outcome` (`answered`, `unverified`, `not_found`, `conversational`, or `error` when the question raised; `grounded` and `abstained` are derived from it)
- `grounded`
- `abstained`
- `citations`
- `source_correct`
- `keyword_hits`
- `max_retrieval_score`
- `unique_sources_top5`
- `failure_labels`
- `retrieved_sources` / `context_sources` (ordered source IDs retrieved, and those passed to the LLM)
- `failure_stage`
- `latency_ms`

`failure_stage` attributes each case to the first pipeline stage that lost the expected evidence, so ranking errors and generation errors are reported separately:

| Stage | Applies to | Meaning |
|---|---|---|
| `ok` | all | answerable: all expected sources cited; negative: abstained |
| `retrieval_miss` | answerable | an expected source was never retrieved |
| `context_miss` | answerable | retrieved, but filtered out before the prompt (context score threshold) |
| `false_abstention` | answerable | expected evidence reached the LLM, but the system abstained |
| `citation_miss` | answerable | expected evidence reached the LLM, answer did not cite it |
| `false_answer` | negative | the system answered instead of abstaining |
| `error` | all | runtime failure |

The summary adds `failure_stage_counts` and `abstention_by_negative_type`.

It writes a run artifact to `eval/results/run_<timestamp>.json` and per-question traces to `eval/results/traces/<run_id>/`.

Important caveat:
- harness results depend on the live local generation backend
- model selection is explicit/configurable: `--model` wins, then `RCA_EVAL_MODEL`, then normal `RCA_GENERATION_MODEL` settings
- if Ollama or another configured endpoint is unavailable, the run is not comparable to a normal local run
- after changing the corpus, the right source of truth is a fresh local rerun, not an older checked-in artifact

Failure labels are compact diagnostics emitted by the generation flow and carried into eval output. Current labels include `missing_citation`, `invalid_citation`, `unsupported_claim`, `low_retrieval_confidence`, `low_rerank_score` (pre-generation rerank gate), `rerank_unavailable` (the reranker failed, so that gate could not run), `llm_abstained`, and runtime labels such as `empty_retrieval` or `error`.

## Retrieval Ablations

```bash
uv run python eval/run_ablations.py
```

The ablation runner evaluates retrieval only on the `90` answerable questions and skips the `10` negatives.

It writes the aggregate artifact to `eval/results/ablations.json`.

Current local run:
- `eval/results/ablations.json` (local, not committed)

Aggregate retrieval results:

| Configuration | hit@5 | hit@10 |
|---|---:|---:|
| 0. fts5-only (BM25 baseline) | `95.6%` | `98.9%` |
| 1. vector-only (dense baseline) | `84.4%` | `91.1%` |
| 2. vector + keyword (FTS5) | `84.4%` | `91.1%` |
| 3. vector + keyword + expansion | `95.6%` | `96.7%` |
| 4. full pipeline (+ rewrite) | `95.6%` | `98.9%` |
| 5. production path (query-type aware) | `98.9%` | `98.9%` |

Run 2026-10-02 on the `129`-question set (`90` answerable retrieval cases; negatives are skipped), `gemma3:12b` rewrite. Config 5 mirrors `GenerateFlow`: rewrite is skipped for proper-noun queries and the query type is passed to `RetrieveFlow`; it reuses config 4's rewrite, so it adds no LLM calls. hit@k requires *all* expected sources in the top-k, so two-source cross-paper questions are the strictest cases. Configs 3–5 take hit@5 from a `limit=5` call (as `GenerateFlow`) and hit@10 from `limit=10`, because truncation is limit-dependent. Table: reserved slot on with the default floor.

Reserved new-source slot (#9). One paper's chunks often filled the whole top 5. Keeping the top 4 as ranked and giving slot 5 to the best-ranked unseen paper scoring above the floor:

| hit@5 / hit@10 | reserve off | reserve, no floor | reserve, floor `-6.0` (default) |
|---|---:|---:|---:|
| 3. vector + keyword + expansion | `94.4%` / `96.7%` | `96.7%` / `97.8%` | `95.6%` / `96.7%` |
| 4. full pipeline (+ rewrite) | `94.4%` / `98.9%` | `95.6%` / `98.9%` | `95.6%` / `98.9%` |
| 5. production path | `96.7%` / `98.9%` | `98.9%` / `98.9%` | `98.9%` / `98.9%` |

- Production misses at hit@5 go from `cross-004`, `cross-008`, `densepack-001` (`87/90`) to `cross-004` (`89/90`, Wilson 95% `94.0%`–`99.8%`); cross-paper bucket `75%` → `87.5%`. Reserve-off reproduces the earlier numbers exactly. All runs 2026-10-02, Chroma backend, no failed LLM calls.
- What reaches the LLM: on captured candidate pools, every reserved hit also passes `GenerateFlow`'s context filter (`src:` node or fused score `> 0.55`), so context-level hit@5 equals bundle hit@5 and no context comes back empty.
- Why a floor: without it, `55` of `83` single-source questions get an unrelated paper in slot 5 (median rerank score `-6.0`). The `-6.0` floor keeps both fixes (reserved hits at `-4.3` and `-1.0`) and cuts that to `25`; same-paper chunks in context average `3.82` (no reserve: `4.10`; no floor: `3.52`). The floor was picked on the same 90 questions with only two positives, so treat it as a heuristic. A floor at the abstention threshold (`-3.618`) loses `cross-008`.
- Rejected alternatives: a per-paper cap of 2 on every query (same `89/90`, depth `2.48`); capping only "comparison" queries (a keyword detector had 7 false positives and 3 misses on the golden questions).
- Remaining miss `cross-004` names "the VLM survey", whose first chunk ranks 17th of 27 candidates: an aliasing gap, not ranking.
- Not yet measured: effect on answer quality. Compare with `RCA_RETRIEVAL_RESERVE_NEW_SOURCE=false` in a full harness run. Dense-only rose from `76.7%` (April run) to `84.4%`; the cause has not been isolated (index rebuilt since).

Interpretation guidance:
- FTS5/BM25 is the production lexical backbone and should be treated as the main sparse baseline
- dense retrieval remains useful, but on this corpus the lexical signal is often very strong
- source expansion and the cross-encoder reranker are the main reasons the composed pipeline improves on simpler hybrids
- query rewrite is a small append-only expansion; applied to every query (config 4) it ties expansion-only at hit@5, but applied as in production (skipped for proper nouns, config 5, with the reserved new-source slot) it is the best configuration at `98.9%` hit@5

## CI Retrieval Gate

`tests/integration/test_retrieval_gate.py` runs in the normal pytest job (CI and pre-push) and fails when a change pushes fixture questions down the ranking. It needs no Ollama, model download, or network.

- **Corpus:** 12 synthetic markdown notes in `tests/fixtures/retrieval_gate/corpus/` (robotics topics with overlapping vocabulary, plus two long generic notes that crowd the top 5). Questions with expected sources are in `questions.json`: 27 in all, 6 needing two sources.
- **Path:** the same `RetrieveFlow.retrieve(query, limit=5, query_type=classify_query(query))` call `GenerateFlow` makes, with the vector store forced onto its JSON backend, reranker off, no rewrite, and every retrieval setting pinned so a local `.env` cannot change the result.
- **Check:** each question's rank (hit position of its last expected source in the top 5, duplicates of a paper included) is compared with `baseline.json`. The test fails if any question ranks worse, even when others improve, and prints `hit@5` and MRR before → after plus every question whose rank moved. A trade-off therefore needs a deliberate baseline refresh, and the `baseline.json` diff shows it in review.
- **Baseline:** `hit@5 96.3%` (26/27), MRR `0.717`. `rg-25` is a recorded miss: one long note fills all five slots, and the reserve slot only works with the reranker. After a deliberate retrieval change, refresh with `RCA_UPDATE_RETRIEVAL_BASELINE=1 uv run pytest tests/integration/test_retrieval_gate.py` and commit the `baseline.json` diff with the change. Do not leave the variable exported: every run, including pre-push, would rewrite the baseline and pass.

Checked by breaking the real code (2026-10-04):

| Breakage | Caught | How |
|---|---|---|
| `_lexical_score` returns 0 | yes | 3 questions leave top 5, MRR 0.717 → 0.601 |
| score sort reversed | yes | 4 leave top 5, MRR → 0.361 |
| `LEXICAL_TEXT_WEIGHT` = 0 | yes | MRR → 0.612 |
| `LEXICAL_BASE_SCORE` 0.45 → 0.2 | yes | MRR → 0.676 |
| proper-noun lexical base 0.65 → 0.10 | yes | MRR → 0.714 |
| query type ignored (`None`) | yes | rg-24 3 → 4 although MRR rises to 0.751 |
| conceptual lexical base 0.30 → 0.45 | no | |
| `LEXICAL_TITLE_WEIGHT` = 0 | no | FTS candidates already come from the target note |
| stopword list removed | no | |
| vector search disabled, or score scale 0.5 | no | the JSON fallback is weak; with it disabled the fixture scores higher (MRR 0.760) |

So the gate covers FTS5 candidates, lexical scoring, and tokenisation; it does not cover the vector component or most query-type weights. Also not covered: query rewrite (needs an LLM; the 72f71a3 rewrite regression would not have been caught here), cross-encoder rerank, real embeddings, source expansion, and the reserve slot. Without the reranker the call fetches only 5 candidates, so expansion and the reserve slot cannot change which sources are in the top 5. The reserve slot keeps its unit tests; the full path is measured by the ablations above.

## Coefficient Sweep

```bash
uv run python eval/run_coefficient_sweep.py
```

The held-out coefficient sweep tunes the lexical reranker used before merge and expansion.

Current split behavior:
- split files live in [eval/splits/dev.json](../eval/splits/dev.json) and [eval/splits/test.json](../eval/splits/test.json)
- the split is stratified by category with `random.seed(42)`
- the script now scales the held-out size with the corpus instead of hardcoding the original `45 / 20`
- for the original 100-question corpus, the split was `69` dev / `31` test; the 29 negatives added later were appended with the same seed and ratio (`20` dev / `9` test) so existing assignments stay stable, giving `89` dev / `40` test. Rerunning the sweep regenerates the full stratified split.

As with the other eval scripts, rerun locally when the corpus or retrieval backend changes.

Note:
- the coefficient-sweep script itself was fixed to track the current retriever signature and current corpus size
- if the sweep is run in a sandboxed environment that forces JSON fallback, do not treat those numbers as comparable to the live Chroma/Ollama runs above

## Multi-Model Matrix (Ollama)

To compare model behavior beyond a single default model, run a matrix benchmark.

```bash
uv run python eval/run_model_matrix.py \
	--models gemma3:12b gemma4:e4b llama3.1:8b qwen2.5:14b \
	--pull-missing
```

Output artifacts:
- per-model harness runs in `eval/results/run_<timestamp>.json`
- aggregate matrix in `eval/results/model_matrix.json`

Model onboarding recommendation:
- keep at least one local baseline that fits in RAM next to normal work (`qwen3.5:4b`)
- test 1 fast/small model for latency-sensitive scenarios
- test 1-2 alternate instruction-tuned models for citation and abstention variance
- compare both quality (`citation_precision`, `abstention_recall`) and cost proxy (`average_latency_ms`)

Current model-selection verdict:
- Production default is `qwen3.5:4b` for both chat and agent mode (2026-11-09, see below); `gemma3:12b` was dropped because it left the laptop swapping.
- Split-model rewriting is retained as a research option but is not recommended for production. On this corpus it increased latency by 10s+ while improving citation precision by under 2 points and keyword hit rate by about 1 point.
- `gemma4:e4b` was evaluated as a candidate default and rejected for daily use due to high latency and elevated answerable abstentions despite stronger citation precision.

### Citation reminder prompt (2026-11-09)

Two prompt changes for small models that answered in uncited prose: every context header spells out the tag to copy (`[chk:...] Title (cite as [[chk:...]])`), and a short citation reminder follows the question. Dev split, answerable questions only (62); "cited refusals" are grounded answers that contain one of `_ABSTENTION_SIGNALS` (the model refuses but cites a nearby block anyway), counted separately because they are not real answers.

| prompt | model | real cited answers | cited refusals | negatives refused (27) | keyword hit rate | s/question |
|---|---|---|---|---|---|---|
| old | `qwen3.5:4b` | 21 | 3 | 25 | 0.251 | 5.0 |
| new | `qwen3.5:4b` | 40 | 18 | 12 | 0.264 | 6.3 |
| old | `qwen3.5:2b` | 45 | 2 | 21 | 0.268 | 4.3 |
| new | `qwen3.5:2b` | 45 | 14 | 13 | 0.247 | 3.3 |
| old | `gemma3:12b` (30-question subset, 21 answerable) | 20 | 0 | 6/9 | | 30.2 |
| new | `gemma3:12b` (same subset) | 17 | 0 | 7/9 | | 77.1 (laptop swapping) |

For the default `qwen3.5:4b` the reminder nearly doubles real cited answers (21 → 40 of 62); for `qwen3.5:2b` it only turns refusals into cited refusals; `gemma3:12b` (since removed) lost 3 of 21 on a small subset. The cost is on refusals: the model now cites even when it says the context lacks the answer, and `_decide_abstention` treats a hedge with valid citations and retrieval score ≥ 0.5 as an answer, so negatives refused fall from 25 to 12 and the UI shows such refusals as grounded answers. The summary metrics overstate the gain for the same reason (grounded rate over all 89 cases 0.28 → 0.82, citation precision 0.49 → 0.97, answerable abstentions 15 → 3: about 9 of those 15 still refuse in substance). Fixing the hedge-plus-citation case is a separate change in `_decide_abstention` (#6).

Rejected variants: a worked example in the system prompt (`qwen3.5:4b` grounded 0.80, precision 0.91) and asking for a bare refusal with no citations (the model ignored it; two degenerate "no , no" answers). Artifacts: `eval/results/bakeoff_20261109/prompt/` (local only).

### Full chunk text in the prompt (2026-11-09)

Until now the answer model saw only the first 240 characters of each retrieved chunk (`RetrievalHit.excerpt`, cut in `RetrieveFlow` since the first commit), although chunks average about 1,100 characters; the answer often sat just past the cut. The prompt and the post-generation support check now use the full node text; the cross-encoder and the UI keep the 240-character excerpt, so the rerank-gate threshold (−3.618) is unchanged. Dev split, `qwen3.5:4b`, citation reminder in both runs:

| context per hit | real cited answers (62) | cited refusals | negatives refused (27) | answerable abstentions | keyword hit rate (answerable) | s/question | prompt tokens per generation call, mean / max |
|---|---|---|---|---|---|---|---|
| 240-char excerpt | 40 | 18 | 12 | 3 | 0.264 | 6.3 | 1110 / 1346 |
| full chunk | 51 | 6 | 14 | 4 | 0.484 | 9.6 | 2193 / 2665 |

The keyword hit rate, long read as a retrieval or rewrite weakness, nearly doubles: it measured answer content, and the model could not state what it was never shown. Part of the gain may be length (answers are about 22% longer and the metric scans the whole answer), and both are single runs at temperature 0. Context length is not a constraint for the default model: probed on Ollama 0.40.15, `qwen3.5:4b` (MLX runner, 262,144-token model context) evaluated a 28,923-token prompt in full and still followed its system rule, so long conversation history is not cut. The 4,096-token default may still apply to models on the llama.cpp runner; that was not probed. Not re-run: other models, the test split, and the agent's `search_knowledge_base` tool, which still returns 240-character excerpts. Side effects: the post-generation support check (two shared content tokens with the cited text) now compares against about five times more text, so it rejects even less: replayed offline on this run, an answer written for a different question passes it 96% of the time (68% with excerpts). `unsupported_claim` fired in neither run; a real claim check is #6. The paper node (`src:`) holds the same opening text as its chunk 0, and 39 of 89 prompts carry both, about 300 duplicate tokens. Artifact: `eval/results/bakeoff_20261109/fulltext/qwen3_5_4b/` (local only).

## Known Limitations

- Keyword hit rate (`20.5%` on the old 100-question run) was long read as the primary retrieval weakness; most of it came from the answer model seeing only 240 characters per chunk (see "Full chunk text in the prompt"). With full chunks `qwen3.5:4b` reaches `0.484` on the dev split.
- "✓ Cited" means cited, not checked: about one cited sentence in four is not fully backed by the block it cites, and no support check tried so far meets the bar for a "Supported" badge (see "Citation Support Labels").
- Split-model rewriting has been evaluated and rejected for production due to latency cost versus marginal gains.
- Answers that say the context does not answer the question but still give part of an answer (`contradictory` in Answer Outcome Labels) pass as grounded answers; the abstention decision cannot tell them from refusals that cite a nearby block (#6).

## Response Structure Conformance (Gemma rollout)

To avoid losing current UI-model integration context, we now track response-shape regressions explicitly.

Observed examples from recent comparison:
- Some responses include bullet-heavy markdown prefixes (for example `* **Jampacker:**`) that look noisy in compact answer views.
- Some responses emit mixed citation grouping such as `[[chk:...], [src:...]]`, which does not align cleanly with the expected inline citation chip pattern.
- Less-structured responses from other models can omit explicit source markers entirely, reducing citation usability.

Why this matters:
- The UI currently renders source references as end-of-answer source buttons/chips.
- Citation shape drift from the model can reduce parsing quality and degrade consistency across models.

Current plan item:
- Add a response-structure validation pass to the v2 plan and treat citation-shape conformance as a release-check criterion for model onboarding.

Minimum acceptance checks for a model profile:
- Inline citations resolve to valid source IDs or chunk IDs that can be normalized to source IDs.
- Bullet/markdown formatting does not break answer readability in the chat surface.
- Extracted citations map correctly to right-panel/source-button behavior.

## Agent Evaluation


`eval/run_agent_eval.py` runs the multi-turn agent on the 20 tasks in `eval/agent_tasks.json` (knowledge base 6, filesystem 4, experiments 4, multi-step 4, refusal 2). Each run is sandboxed: filesystem tools see a temporary copy of `eval/agent_fixture/`, experiment tools see a freshly seeded DB (`SEED_RUNS`), and knowledge-base search uses the live corpus read-only. ## Run Provenance and Comparing Runs

Every eval artifact (harness `run_*.json`, `ablations.json`, `retrieval_features_*.json`, `coefficient_sweep.json`, `agent_eval_*.json`) carries a `provenance` block from `rca/telemetry/provenance.py`; the calibration report copies the provenance of the feature file it read (`features_provenance`). Harness traces get `corpus_version`.

| Field | What it pins down |
|---|---|
| `corpus.corpus_version` | 16-hex SHA-256 prefix over every indexed source and chunk (ID, title, text, metadata) and every edge, plus counts |
| `models` | Ollama server version and the exact digest of each model used (`null` = not installed) |
| `reranker` | cross-encoder name and the cached Hugging Face revision |
| `settings` | retrieval/generation settings that change results (reranker, limits, reserve slot, chunking) |
| `code` | git commit, whether the tree was dirty, and a hash of the uncommitted diff |
| `index_start` / `index_end` | vector backend and record count at run start and end |
| `index_degraded_during_run` | `true` if the backend, its warning or its count of fallback calls changed between start and end, so a store that fell back and recovered mid-run still counts (a run that started on the JSON fallback shows that in `index_start` instead) |

Compare two runs only when `corpus_version`, the model digests, the reranker revision, and `settings` match; treat any run with `index_degraded_during_run: true`, or `index_start.backend` other than `chroma`, as invalid. The fingerprint hashes node content instead of `source_revisions` because sources ingested before revision tracking have no revision rows (24 of the current 25).

## Abstention Calibration (retrieval features)

Retrieval-only study, no answer generation. Run on 2026-10-01 over all `129` questions with the production retrieval path (`gemma3:12b` query rewrite, `nomic-embed-text`, cross-encoder rerank, `limit=5`).

```bash
uv run python eval/collect_retrieval_features.py          # -> eval/results/retrieval_features_<ts>.json
uv run python eval/calibrate_abstention.py eval/results/retrieval_features_<ts>.json
```

`collect_retrieval_features.py` mirrors the retrieval half of `GenerateFlow.generate_answer()` and records per-question signals: fused hit scores, raw cross-encoder `rerank_score`s, score gap/spread, source concentration, and per-stage maxima. `calibrate_abstention.py` picks a single-feature threshold on the dev split that maximizes negative recall with at most `5%` answerable false abstentions, then reports it once on test. Pairwise rules were tried and dropped: they overfit the `27` dev negatives.

Findings:
- The current retrieval gate (`max_score < 0.50`) abstains on `0/39` negatives. Fused scores are capped at `0.95` and rarely fall below `0.50`, so earlier abstention came entirely from the LLM hedge-phrase gate.
- The raw cross-encoder score is the strongest signal (dev AUROC: `rerank_mean` `0.85`, `rerank_max` `0.84`, `top_source_share` `0.75`, `unique_sources` `0.72`, fused `max_score` `0.63`).
- Selected rule `rerank_max <= -3.618`: dev `12/27` negatives with `2/62` false abstentions; test `5/12` negatives with `1/28` false abstentions.
- By type (all 39): `off_domain` `4/4`, `out_of_corpus` `3/4`, `unreported` `3/10`, `false_premise` `2/7`, `fabricated` `1/4`, untyped `4/10`. Retrieval signals catch questions whose topic is absent; they cannot catch questions about papers that are present (unreported details, false premises), which need the generation-side grounding check.

Rechecked 2026-11-11 with the shipped rewrite model (`qwen3.5:4b`, commit `fb78227`, reserved slot on, Chroma, corpus `51b6785c3405cb16`): dev selects the same rule, `rerank_max <= -3.618`, at the same `12/27` negatives and `2/62` false abstentions; on test it catches `5/12` with `0/28` false abstentions (was `1/28`). The threshold therefore stays. Artifacts: scratchpad only, not committed.

Features were collected before the reserved new-source slot (#9); `rerank_max` and the selected rule are unaffected (the top hit is never replaced), but `unique_sources` / `top_source_share` AUROCs would shift on a rerun.

Caveats: `12` test negatives is small, so test recall has a wide confidence interval; the rule is wired into `GenerateFlow` as a pre-generation gate (2026-10-01), but harness abstention metrics stay unchanged until a full rerun. The threshold is specific to `cross-encoder/ms-marco-MiniLM-L-6-v2` logits and must be recalibrated if the reranker changes.

## Answer Outcome Labels (#6)

Why: `GenerateFlow` decides "answer" or "abstain" from hedge phrases plus citation validity. With the citation reminder, small models write "the context does not contain X ... [[source]]", which passes as a grounded answer whether or not the cited part helps. Answers that state a gap and then give useful information are a third outcome, not a refusal. Before choosing a classifier (current rule, self-declared status via structured output, claim-level entailment check), we need human labels on real answers to measure any of them against.

Sample: `eval/sample_answer_labels.py` draws about 100 saved answers from the 2026-11-09 dev-split runs, weighted towards hedged answers, and writes `eval/answer_labels.json`. Answers produced by the pre-generation gates (empty retrieval, rerank gate) are left out, because the classifier never sees them. The file stores context node IDs, not paper text. Labels are judged against what the model saw: only the first 240 characters of each context chunk (`excerpt` in `rca/flows/retrieve_flow.py`), read from the local graph store. All `--run` arguments share one seeded generator, so changing the order or count of one run reshuffles the later ones.

Labels (one per answer, judged against the question and the retrieved context only):
- `answered`: gives the information the question asks for, taken from the context. Minor omissions are fine.
- `partial`: says some of what was asked is not in the context, and gives information that answers another part of the question or corrects its premise (e.g. "SayPlan is not evaluated outdoors; it is evaluated in multi-floor indoor buildings").
- `not_found`: says it cannot answer. Anything else in it is background that does not answer any part of the question (e.g. "the license is not stated; the text mentions a different paper's license"), whether or not it is cited.

Test for `partial` vs `not_found`: would the user learn something that answers part of their question, or shows why it cannot be answered as asked? Yes means `partial`; background only means `not_found`.

Rules settled with the project author on unclear cases (2026-11-09):
- On an unanswerable question, a premise correction counts as `partial` only when the answer says outright that the premise is wrong ("JSON schemas, not XML"). A hint the reader has to infer ("the paper describes GAD as a decoding method", "SayPlan plans across multiple floors") is filler, so `not_found`.
- A real fact about the subject does not make it `partial` when the comparison or setting asked about does not exist (AutoBag's real success rates for a made-up SuctionGrasp comparison).
- An answer that says the context does not answer the question at all (anywhere in the answer) and still gives part of the answer is a bad response, not just a partial one: it keeps the `partial` label (the user does learn something) and gets `contradictory`. A good partial answer says which part is covered and which is not.

Flags, independent of the label:
- `unsupported`: the answer states a fact that the retrieved context does not support (invented or wrong detail). Judged on what is shown to the model, not on the full paper.
- `contradictory`: see above.
- `missed_in_context`: the answer says something is absent although the shown context contains it. None in this sample once judged against the 240-character excerpts.
- `unsure`: the labeller could not decide; these go to a second person.

How the labels will be used: classifier agreement with the label (three classes, and two classes with `partial` merged into `answered`), reported separately for answerable and negative questions. For negatives, `not_found` and premise-correcting `partial` are both acceptable; `answered` or `unsupported` is a failure. Every candidate classifier is designed on these dev-split labels and reported once on a separately labelled test-split sample, so the dev labels are not also the score.

Bias: first-pass labels are drafted by the same assistant that wrote the classifiers (`labeled_by` field) and `unsure` cases are reviewed by the project author; a fully human-labelled subset would be stronger.

First result, 100 answers (seed `20261109`; 35 `qwen3.5:4b` and 15 `qwen3.5:2b` with the citation reminder, 5 with the v3 refusal wording, 50 from the old prompt across `qwen3.5:4b`, `qwen3.5:2b`, `gemma3:12b`, `qwen3:4b`, `ministral-3:3b`). Hedged answers are weighted 3× in the draw, so these counts describe the sample, not how often each case happens in normal use.

| | answerable (69) | unanswerable (31) |
|---|---|---|
| `answered` | 20 | 1 |
| `partial` | 25 (17 `contradictory`) | 3 |
| `not_found` | 24 | 27 |

How the current `GenerateFlow` decision (abstain or answer) matches, with `answered` and `partial` merged as "useful":
- useful answers shown as answers: `46/49`;
- `not_found` answers caught as abstentions: `13/51` (`6/27` on unanswerable questions, `7/24` on answerable ones); the other `38` reach the user as answers (`37` marked grounded);
- two-class agreement: `59/100`.
- `unsupported`: 7 answers, all from the old prompt (`qwen3.5:2b`, `qwen3.5:4b`, `qwen3:4b`, `ministral-3:3b`); none from the citation-reminder runs.

## Citation Support Labels (step 12)

Why: the "✓ Cited" badge means the answer cites a block it was given and shares two content words
with it. It does not mean the cited block says what the sentence says. The question here is
whether a check can earn a "Supported" badge: per cited sentence, does the cited passage state
it?

Labels: `eval/sample_support_labels.py` splits the full-text `qwen3.5:4b` answers already
labelled for #6 into sentences (every useful answer on test, 27; a seeded 25 of 55 on dev) and
adds one swapped citation per answer (a cited sentence paired with another block the model saw,
the wrong-citation error). Each sentence is labelled against the full text of the blocks it
cites, as the model saw them: `supported` (every detail stated), `partial` (some detail, such as
a number, name, cause or attribution, missing or different), `unsupported`, or `no_claim`
(heading, list intro, gap statement). A sentence that states a gap and also a fact is labelled on
the fact. Uncited sentences are labelled against all blocks the model saw. Files:
`eval/support_labels_{dev,test}.json` (node IDs only, no paper text). Test labels were written
before any check ran on test; the break-it review then found two test labels inconsistent with
these rules (`synth-003#2`, `stablebinpacking-005#2`, both `supported` → `partial`), and the
test numbers below are rescored from the same run's predictions with the corrected labels.

| | dev | test |
|---|---|---|
| natural cited sentences that make a claim | 60 (16 partial or unsupported) | 79 (22) |
| swapped citations that make a claim | 24 (all not supported; 1 partial) | 25 (all not supported; 6 partial) |
| uncited sentences that state a fact | 24 (2 partial) | 21 (3 partial or unsupported) |

So about one cited sentence in four is not fully backed by the block it cites (dev 16/60, test
22/79). Typical cases on
test: one table's scores reported as another benchmark's (`sgvl-003`), facts from a figure in
chunk 0016 cited to chunk 0017 (`vlmsurvey-004`), "the baseline reached 98%" where 98% is the
method and the baseline 83% (`densepack-003`).

Checks (`eval/compare_support_checks.py`), each judging one cited sentence against its cited
text with `qwen3.5:4b` at temperature 0:
- `overlap`: the current word-overlap rule, per sentence.
- `llm_verdict`: the model returns `supported` / `partial` / `unsupported` / `nothing_to_check`.
- `llm_quote`: the model first copies the shortest part of the passage that states the sentence;
  supported only if the verdict says so and 80% of the quote's 4-word runs are in the passage.

The bar, fixed before the test run: catch at least 80% of not-supported cited sentences, keep at
least 85% of supported ones, at most 3 s added per answer. Two prompt rounds on dev. Round 1
found that real quotes failed an exact match (two sentences joined, a PDF hyphen kept, markdown)
and that "it states X but not Y" sentences were judged on the missing Y; round 2 matched quotes on
4-word runs and told the model to ignore "not stated" parts. A one-call-per-answer variant was
slower and worse and was dropped. Dev round 2: `llm_verdict` caught 31/40 (natural 8/16), kept
39/44, 3.3 s per answer; `llm_quote` 34/40 (natural 11/16), 29/44, 4.6 s.

Test, one run (Wilson 95% intervals; time is the median per answer, the model loaded). Kappa is
given over all cited claims and over natural sentences only; the swapped ones are all not
supported, which raises the first:

| | caught (natural + swapped) | natural only | swapped only | kept | kappa (all / natural) | time |
|---|---|---|---|---|---|---|
| `overlap` | 3/47 (6%) | 0/22 | 3/25 | 57/57 | 0.07 / 0.00 | 0 |
| `llm_verdict` | 36/47 (77%, 63–86%) | 15/22 | 21/25 | 52/57 (91%, 81–96%) | 0.69 / 0.61 | 4.1 s |
| `llm_quote` | 41/47 (87%, 75–94%) | 18/22 | 23/25 | 42/57 (74%, 61–83%) | 0.60 / 0.48 | 7.4 s |

No check passes. `llm_verdict` misses the catch bar and the time bar; `llm_quote` catches enough
but drops one supported sentence in four and takes 7.4 s. `llm_verdict` lets the clearest
error on test through as supported (`sgvl-003`, VSR scores presented as Winoground) and misses subtle shifts of
attribution and purpose; on dev it misses the same kind (a planning rate called an execution
rate, credit moved from pre-training to the decomposition). At answer level, it would mark 11 of
the 25 test answers that cite something as Supported; 9 of those 11 have every cited claim
labelled supported, and 1 also holds an uncited sentence labelled partial.

Decision: **the badge stays "Cited".** A badge that is wrong on about one answer in five it
marks, at 4 s per answer, does not meet the bar set for it. The word-overlap rule behind
"Cited" catches almost nothing (3/47), which is what the badge's name already says.

Caveats: labels, checks and prompts are by the same assistant (`labeled_by: assistant-draft`;
one test item is `unsure`); the dev prompts were tuned in two rounds on 60 natural sentences; 22
natural not-supported sentences on test give wide intervals. A `nothing_to_check` verdict (for a
sentence that only states a gap) skips the check, and on test one `partial` claim passed that
way under each LLM check. Concurrent calls do not cut the
time on this machine: Ollama runs one request at a time (`OLLAMA_NUM_PARALLEL=1`). Not tried: a
larger checker model (a second model in 18 GB of RAM), an NLI model (none installed), checking
uncited sentences. Run outputs: scratchpad only, not committed.

## QASPER: questions written by others (step 17a)

Why: every other number here comes from questions, papers and labels written for this project.
QASPER (Dasigi et al., 2021; CC BY 4.0) has questions written by NLP readers about arXiv papers,
with answers, evidence paragraphs and unanswerable questions. Nothing in RCA was tuned for it.

Setup: `eval/run_qasper.py` takes a seeded sample (seed `20261119`) of 40 papers from the QASPER
test split, fetches their PDFs from arXiv with the step 18 fetcher, builds a separate library
(40 sources, 1,418 chunks; corpus `e87b8bd788b5dd54`) and asks all 147 questions on them with
the shipped defaults (`qwen3.5:4b`, facts check on, Chroma). 117 are answerable (no annotator says
unanswerable), 12 unanswerable (all annotators do), 18 mixed (asked, scored only in the
all-question F1). No run had errors. Two question forms:
- **As written** (run `20261119T123431Z`, commit `9783a6e`): QASPER's text, which is about one
  paper and usually does not name it ("which baselines did they compare against?").
- **Paper named** (run `20261119T125758Z`, commit `a14c5d2`): `In the paper "<title>": <question>`,
  the way a person asking RCA about one of many papers would.
- **Paper named, opening once** (run `20261119T174337Z`, commit `389fcad`): the same, after the
  paper's `src:` node stopped repeating its first chunk in the context (below).

| | as written | paper named | paper named, opening once |
|---|---|---|---|
| answerable: answered citing the paper asked about | 30/117 (26%, 19–34%) | 66/117 (56%, 47–65%) | 75/117 (64%, 55–72%) |
| answerable: refused | 40/117 (34%, 26–43%) | 48/117 (41%, 33–50%) | 36/117 (31%, 23–40%) |
| unanswerable: refused | 8/12 (67%, 39–86%) | 9/12 (75%, 47–91%) | 7/12 (58%, 32–81%) |
| an evidence paragraph in the selected context | 17/109 (16%, 10–24%) | 22/109 (20%, 14–29%) | 30/109 (28%, 20–37%) |
| … of those, in context the model read (a gate can refuse first) | 14/84 | 22/108 | 30/108 |
| token F1, answerable questions | 0.046 | 0.061 | 0.074 |
| token F1, every question (as QASPER's evaluator) | 0.15 | 0.19 | 0.17 |
| median time per question | 11.4 s | 8.4 s | 9.0 s |

Intervals are Wilson 95%. Evidence counts answerable questions with a text evidence paragraph
(tables and figures left out); a match is half of the paragraph's
4-word runs in the context, because QASPER's text comes from LaTeX and RCA's from the PDF.

Reading it:
- **Questions that do not name their paper fail on a library.** As written, RCA answered 75 of
  117 answerable questions, but only 30 from the paper asked about; 41 of the 117 refer to the
  paper only as "they" or "their" and 5 more as "this paper". Naming the paper more than doubles
  the right-paper answers (2.2x).
- **Retrieval finds the paper, not the passage.** With the paper named, 88% of the context
  (513 of 585 blocks) comes from the right paper, yet an evidence paragraph is in it for 22 of 109
  questions. It is not the matcher: on the paper's whole PDF text the same match finds evidence
  for 106 of 109. Over all 86 misses, a median 93% of the evidence's 4-word runs are in the paper
  and 0.8% in the context (17 misses above 3%, 4 near misses at 44 to 49%).
- **The opening of the paper fills the context.** Chunk 0 ranks first for 92 of 117 answerable
  questions, and the paper's `src:` node, whose text is the same as chunk 0 in all 40 papers,
  usually follows it, so two of five slots carry the same opening text. Why chunk 0 wins is a
  hypothesis, not measured: every chunk's title is `<paper title> #N`, so title words lift all
  of a paper's chunks equally, but chunk 0's text also holds the title, and the cross-encoder
  scores only each hit's first 240 characters, which for chunk 0 is the title block.
- **Ablation and fix (2026-11-19).** Retrieval only, four configurations on the paper-named
  questions: evidence in the selected context 22/109 as shipped; 23 with the cross-encoder
  reading whole chunks; 30 without the duplicated `src:` node; 33 with both. The opening still
  ranks first in 88 to 92 of 117 in all four, so the title in the question, not the 240
  characters, puts it first. On our golden set the expected paper in the top 5 did not change in
  any configuration; the rerank gate's trade-off did not change without the `src:` node, and
  shifted with whole-chunk input (the threshold would need recalibrating). Shipped: the `src:`
  node is left out when it repeats its first chunk (on by default; dev split 47 to 52 of 62
  answered with the expected citation; test scorecard above). The cost: fewer refusals of every
  kind, so unanswerable questions refused on QASPER fell from 9 to 7 of 12 (two questions,
  `11360385…` and `538430077…`, both with a changed context; our dev split held at 26 of 27).
  Side effects: a `src:` node passed the context filter at any score, so a question whose only
  context was one can now get an empty context (none in 246 questions); and the reserved slot can
  go to a different paper. Our golden top-5 check was 90/90 in every configuration, a ceiling
  that cannot show harm. Not shipped: whole-chunk input (one to three questions here, within
  noise). The ablation's `select_context` skips the conversational shortcut and the rerank gate;
  143 of 147 QASPER questions are proper-noun queries and one is gated in both configurations,
  so this did not change the comparison. Next idea for the opening: use a named paper to
  choose the source and rank its chunks by the rest of the question.
- **Refusals follow.** With the right passage missing, the model often says the context does not
  answer (41% of answerable questions refused with the paper named, 31% after the fix below). The 12 unanswerable questions are too few to read
  much into the refusal rate.
- **Token F1 is low by construction** and not comparable to QASPER papers that read the whole
  paper: gold answers are short spans or yes/no (19 of 117), RCA writes sentences.
- **Against the scorecard** (96% retrieval hit@5 and 86% answered with the right citation on our
  own test split): hit@5 there counts the right paper in the top 5, a weaker test than the
  passage match here, and our questions name their paper and use its terms. Which of the
  differences explains the gap is not measured.

Caveats: one run per form; 40 papers; the first full run answered from the wrong library and is
not reported (its file, `qasper_20261119T120620Z.json`, stays local; fixed in `dabd0c7`, see
CHANGELOG). Data, PDFs, library and run files are under
`eval/external/` and `eval/results/` (not committed).

## Ingest by origin (step 17b)

What backs each kind of input, checked 2026-11-20:

| Origin | Evidence | Result |
|---|---|---|
| arXiv two-column PDFs (ACL style) | QASPER library, 40 papers | evidence paragraphs found in the PDF text for 106 of 109 questions (4-word-run match against QASPER's LaTeX text) |
| Publisher PDFs (IEEE, MDPI) and reports | the user's library, 25 sources | scorecard retrieval 27/28 |
| A long document | generated 300-page PDF, one 2,600-character line of text a page, temp library | 899 chunks in 17 s with `nomic-embed-text`; a sentence from page 250 retrieved in the top 5 |
| A scanned PDF (no text layer) | generated blank pages | refused with a message (was: accepted as an empty source) |
| A partly scanned PDF | text cover page and blank pages | ingested; the Library says "3 of 4 pages have no text (scanned?)" |
| Notes, experiment files, git repositories | extractor and ingest tests | refused when there is not a single letter or digit: an empty note, a note of only `#` or invisible characters, an empty or `{}` JSON or YAML experiment file |

Limits: no OCR; tables and figures are read only as whatever text the PDF holds (QASPER's
table-only evidence was left out for that reason); the long-document check is synthetic, one line
of text per page; a PDF whose only text is page numbers passes the check; PDFs already in the
library get their page counts only when their content changes.

## Distilling the facts check (step 15)

Question: can a small model make the facts check's decision (on a hedged reply: useful, or
decline) instead of the second `qwen3.5:4b` call? Result: **no, not this one.** It catches every
decline but drops many useful partial answers (4 of 6 on test, 26 of 58 on held-out papers), so
the LLM call stays.

Set-up (`eval/distil_facts_check.py`, design in the plan):
- Teacher labels: 600 seeded library chunks (seed `20261121`), three generated questions each
  (answered by the chunk, not answered, false premise), asked through `GenerateFlow` on a copy of
  the library with the shipped facts check, commit `f91197b`. 1,800 questions, 1,749 reached the
  model, 978 hedged and labelled by the check: 726 declines, 252 useful. 3 questions were dropped
  as close to a golden question, 4 more at training time as close to a hand-labelled one; the
  nearest trained question to any test question has word overlap 0.33 at most, and none is a
  paraphrase (the closest pair, both about ViLaIn's symbolic planner, asks different things).
- Hardware: built and trained on knuth (RTX PRO 6000 Blackwell) with the laptop's exact model
  files (MLX nvfp4 build) on Ollama 0.40.15. On 30 chunks run on both, knuth agreed with the
  laptop on the check's decision 39/44 times and with a second knuth run 38/40 times: the runner
  is not deterministic at temperature 0, and at this size there is no clear extra difference from
  the machine.
- Student: `cross-encoder/ms-marco-MiniLM-L-6-v2` (22M), question and answer as a pair,
  binary cross-entropy, 4 epochs, 5 of 25 papers held out. Dev hand labels picked epoch 2 (tied with
  epoch 3 at 25/31; ties go to the earlier) and the threshold (0.311). The test hand labels were scored once, afterwards.

Hedged hand-labelled answers (the only ones the check sees), useful = `answered` or `partial`:

| | facts check (LLM, offline run of 2026-11-09, same 14 test answers) | student |
|---|---|---|
| test: declines caught | 8/8 | 8/8 |
| test: useful kept | 5/6 | 2/6 |
| test: agree | 13/14 | 10/14 |
| dev: agree (student threshold tuned on it) | 24/31 | 25/31 |
| held-out papers: agrees with the teacher | | 158/194 (81%) |
| time per answer | 1.7 s median in the step 3 run | 9 ms CPU, 69 ms MPS (M3 Pro, one answer at a time) |

The ship bar, set before training, was test at least 13/14 with no decline missed and held-out
agreement at least 90%. It fails both. In the whole test pipeline the student would keep 23 of
27 useful answers instead of 26.

What the numbers say: the student learned "a hedge means decline" well (8/8 test, 126/136
held-out declines) and partial answers badly (32 of 58 held-out useful replies kept). Those are
the answers that say something is missing and then give part of it; the teacher tells them apart
by listing the facts the answer gives, which a 22M classifier reading the whole reply does not
reproduce from 252 useful examples. Small numbers: 14 test answers, 6 of them useful, so 2/6
versus 5/6 is a big gap on very few cases.

Not tried (each would need a new held-out split, since this one has been looked at): weighting
the useful class (726 to 252), more useful examples (more false-premise questions, which gave the
most), a larger encoder, or distilling the facts list instead of the decision. Artifacts (teacher
JSONL, model, `student.json`): scratchpad and knuth only, not committed. The laptop's stopped
partial build (about 290 chunks) is kept apart and not used.

## Current Status

What is true today, independent of any single artifact:
- the golden corpus is now `129` questions (`39` negative)
- the split files cover that full corpus exactly
- the eval schema tests pass against the updated corpus and split files
- abstention has two measured parts: the pre-generation rerank gate (`rerank_max <= -3.618`, rechecked with `qwen3.5:4b` rewrites) and the facts check on hedged replies; an unanswerable question answered without any hedge passes both, so it is still the main open weakness
- on questions written by others (QASPER, 40 unseen arXiv papers), RCA answers citing the right paper for 64% of answerable questions when the paper is named (26% when it is not), and the passage that answers is in the context for 28%: the opening of a named paper still ranks first, because the title in the question matches it; with fewer refusals overall, 7 of 12 unanswerable QASPER questions are refused
- citation support is measured but not checked at answer time: on test, 22 of 79 cited sentences are not fully backed by their block; the best per-sentence check caught 77% of not-supported cited sentences (natural and swapped) at 4.1 s per answer, below the bar for a "Supported" badge
- a human-authored external subset would still be stronger for bias reduction than self-authored or model-authored additions

Known active failure themes:
- citation selection drift on otherwise relevant retrieval bundles
- unsupported questions whose retrieved context still looks plausible enough to evade abstention
- detail-level abstentions on answerable questions
- rewrite-induced drift on some paraphrase and named-entity queries
